# Finite successor qualification and handoff — normative candidate

Version `B6S/1.0.0-candidate.1`, PROPOSED. These are required future evidence
claims, not executed tests. They do not reproduce or certify the unavailable TQ1
39-check catalogue. Contract adoption, actual-subject selection, test execution,
independent acceptance and production commissioning remain separate gates.

## Q00. Selection and evidence discipline

The independently approved static campaign plan identifies the candidate manifest,
exact selected role/source/release/grammar/schema/configuration/platform/supply
subjects, qualified validators/oracles, protected input/custody boundaries, case IDs,
expected predicates and reviewer responsibilities. It cannot select subjects by a
caller `QUALIFIED` marker or depend on future per-attempt result hashes. The first
trust root is an external examiner's actual source/tool/oracle examination, not a
parser/assessor authenticating itself.

Each original attempt retains immutable intent, actual input/output identities,
observer/tool/release/platform identity, relevant original process/FD/syscall/time
observations, exit/failure and cleanup/accounting evidence. Original failed/partial
attempts remain. A later pass is not a replacement receipt. No actual credential,
PII, provider payload or production record is published with the report.

Case reports use `PASS`, `FAIL`, `UNDETERMINED`, `BLOCKED`, `NOT_EXECUTED`, or
`CARRIED_FORWARD`, each with exact identity/scope. No missing case is a pass, no
skipped body proves PostgreSQL/runtime behavior, and repeated normal/sanitizer runs
are not additional unique cases. A negative test PASS means its expected rejection
was observed; it does not make the rejected operation successful.

## Dependency order and finite stop points

1. Adopt S01–S03 only against exact reviewed candidate bytes. Select S04's actual
   campaign subjects/custody/examiner before claiming execution qualification.
2. First bounded work: PB1 codec/entrypoint and Q01–Q09/Q21 for that explicitly
   read-only slice. A slice receipt names those rows and cannot close full B6.
3. Producer and broader controller work follows accepted exact role profiles, then
   Q10–Q16. Do not wire correlation-only APIs around missing proof/authority.
4. Q17/Q18 require approved representative data; Q19 additionally requires separate
   apply scope/authority and adequate implementation. They can progress independently
   of ordinary deployment, but cannot fabricate missing inputs.
5. Q20/Q22 require the real accepted chain. A code/test PASS never supplies actual
   owner/Finance/Ops decisions. Stop at a missing subject/implementation/authority;
   state it precisely, preserve other scoped results and do not add unrelated work.

## Exact representative input and final-analysis requirements

The data owner/snapshot custodian supplies, through existing restricted custody:

- Authorized source and recipients, one explicit Tenant and complete versioned
  `ALL_TENANT_AQGREEN_PARTICIPATIONS` selector with minimal referential closure.
- Immutable consistent allowlisted sanitized snapshot, approved pseudonym scheme,
  observation/MVCC/schema/migration/provider identity, exact table/count/digest
  inventory and BASE_SNAPSHOT manifest; source/data-handling authorization remains
  separate. No PII, secret or production endpoint is put in Git or this proposal.
- Explicit non-default UTC cutoff not after observation. Prefer equality; an earlier
  cutoff needs authoritative effective-dated evidence for every mutable fact used,
  otherwise UNKNOWN/exception remains. Current Area/security/lifecycle is not history.
- Reviewed roots/components/exception dispositions bound to the same snapshot,
  source digest and BASE digest. Null recruiter, payment confirmation and structural
  completion do not establish root, activation or financial authority.

Outputs must retain three distinct D09 sets; accepted/quarantined components;
roots, sponsor/order/correction inputs; topology/simulator input/output; anomalies;
SAME/CHANGED/AMBIGUOUS structural impact; historical commission/payout-state and
loan/graduation/Onyx intersections; accepted exceptions; final-manifest bindings;
and actual final-verification evidence. This is impact accounting, not permission
to rewrite money, infer exact past values or fabricate whole-population completeness.

Existing B6 representative specification/allowlist/VerifyFinal machinery remains
the analysis contract input. The new runtime qualification namespace does not
silently change `FINAL_ANALYSIS` to a successor-shaped substitute. Any needed
analysis-contract adaptation is separately identified/reviewed before use. Two-run
equality and self-hashes alone authenticate neither the data owner nor the approver.

## D10/B7 handoff and production boundary

Existing D10 consumes restricted independently pinned decision, verified-authority
and operational-final files. Before selecting them, owner/Finance/Ops must bind:
actual B6 final verification; reconciliation execution authority; applied native
mapping/placement comparison; historical accounting/authorization exceptions; exact
whole-Tenant/current-Area scope and canonical weekly UTC effective boundary;
prospective/graduation capability choices; database/schema/configuration/assembly
identities; backup/key/certificate restore and recovery evidence; and separately
chosen provider/worker commissioning. Monthly automation remains outside the launch.

Production reader acceptance of a successor qualification receipt requires an
explicitly reviewed bridge to those existing inputs. No automatic format alias or
new `SUCCESS` field supplies that bridge. Keep incompatible/quarantined populations
and post-boundary V1 ledgers fail-closed, preserve pre-boundary V1 history and refuse
silent fallback when commissioned authority disappears. Application deployment,
documentation merge, parser qualification and B6 technical acceptance activate none
of these financial/provider/worker capabilities.
